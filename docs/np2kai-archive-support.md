# NP2kai の zip / 圧縮形式対応について

NP2kai コアが zip 等の圧縮アーカイブに対応しているかの調査結果。
対象: `core/np2kai`（`wx_alpha` ブランチ、remote `bubio/NP2kai`）。

## 結論

- **現在の `wx_alpha` ブランチでは zip 等の圧縮形式に一切対応していない。**
- ただし **過去の NP2kai には zip 展開機能が存在し、2020-03-11 に意図的に削除（purge）されている。**

## 1. 現在のコアの状況（圧縮非対応）

ディスクイメージの読み込みは `diskimage/fddfile.c` の `fdd_set()` で行われ、
すべて**拡張子ベースの判定 + 生バイナリ読み込み**。zip/lzh/gz を解凍して読む処理は
コア（`diskimage/`, `fdd/`, `common/`）に存在しない。

| 種別 | 対応拡張子 |
|---|---|
| FDD | `.d88` `.88d` `.d98` `.98d`、`.fdi`、`.dcp` `.dcu`、`.nfd`、`.vfdd`、XDF/BETA/BKDSK フォールバック |

判定ロジック: `diskimage/fddfile.c:111` `fdd_set()` → `file_getext()` で拡張子を取り
`milstr_cmp` で比較。

## 2. かつて存在した zip 機能（削除済み）

git 履歴に削除コミットが残っている:

```
c0fd97a  purge (zip) archivement function  (AZO234, 2020-03-11)
  - delete 'zlib' directory
  - delete common/arc*.*
  - remove SUPPORT_ARC
  - remove SUPPORT_ZLIB        (43 files changed, +82 / -8441)
```

削除前の構成:

- `common/arc.c` / `common/arcunzip.c` … ZIP アーカイブを開く汎用 I/O 層
  （`arc_open` / `arcex_fileopen` / `arc_fileread` 等のハンドルベース API）
- バンドルされた `zlib/`（inflate 一式）
- **対応していた ZIP 圧縮方式**:
  - `method0`（無圧縮 / stored）… 常時
  - `method8`（deflate）… `SUPPORT_ZLIB` 有効時に zlib で展開
- ビルドフラグ `SUPPORT_ARC` / `SUPPORT_ZLIB` で切り替え（SDL2 / win32 系で有効化）

### 重要: zip 機能はディスクイメージ読み込みには使われていなかった

`SUPPORT_ARC` が配線されていたのは以下のみ:

- `common/textfile.c` … テキスト系設定ファイル
- `sound/vermouth/midimod.c` / `midinst.c` … Vermouth ソフトシンセの MIDI 音色データ

つまり「zip 内の FDI/D88 を直接マウント」する用途ではなく、設定・音色データを
アーカイブから読む用途だった。

## 3. 残存する圧縮関連コード（コア外）

- `sdl/libretro/.../libchdr/`（CHD = CD イメージ圧縮）と libretro-common の
  `archive_file.h` … **libretro バックエンド専用**で、本プロジェクトのビルド対象外。
- `LICENSES/LICENSE-ZLIB.TXT` … ライセンス文書の名残のみ。
- `windows/*.vcxproj` には `..\common\arcunzip.c` への参照が残っているが、ファイル自体は
  削除済みのため stale 参照（本プロジェクトのビルドには無関係）。

## 4. 本プロジェクトへの示唆

zip 対応が必要になった場合:

- **推奨**: コアには手を入れず、**Zig アプリ層で解凍 → 一時展開した生イメージをコアに渡す**。
  `AGENTS.md` の移植性・メンテナンス性重視の方針に合致する。
- **非推奨**: コアに `SUPPORT_ARC` を復活させる方向。削除された依存（zlib・arc 一式）を
  戻す必要があり、メンテナンスコストが高い。

# 圧縮ファイルを解凍して使う場合の設計（write-back 問題）

圧縮されたディスクイメージを解凍して使う場合、エミュ内での書き込み（セーブ、コピープロテクト
処理等）をどこへ永続化するか（write-back）を決める必要がある。本質的には**2つの独立した軸**で
方式が決まる。

## 軸1: 書き込みセマンティクス（write の行き先）

PC-98 ゲームはセーブ・プロテクト処理でディスクに書く。圧縮元には書けないため、解凍後ファイルへの
write の扱いで方式が分かれる。

| 方式 | 概要 | 長所 | 短所 |
|---|---|---|---|
| **A. 破棄（read-only）** | 解凍物をマウント、終了時に破棄。write は揮発 | 単純・元アーカイブ不変 | セーブが消える。多くのゲームで実用不可 |
| **B. 解凍コピーを正本化** | 解凍ファイルがそのまま作業ファイルになり、以後 write はそこに永続化。zip は配布形式扱い | 単純・追加プラミング不要・write が自然に残る | 元 zip と乖離。zip を作り直すとハッシュ変化→セーブ離散 |
| **C. ラウンドトリップ（再圧縮）** | 終了/eject 時に zip へ書き戻し | 単一アーティファクト維持 | 再圧縮コスト・書込中クラッシュで破損・mtime/hash 変化・ユーザの元アーカイブ改変 |
| **D. オーバーレイ / 差分ファイル** | 元は不変（解凍は RAM か read-only）、write は別の差分ファイル（セクタ単位 delta）へ。マウント時に「元 + 差分」を合成 | 元アーカイブ完全不変・セーブが小さい・dedup と相性良 | セクタオーバーレイ層の実装が必要 |

A〜D は「元を不変マスタとみなすか（A/D）／配布形式とみなすか（B/C）」の哲学差。

## 軸2: キャッシュ識別キー（同一性の判定）

| キー | 評価 |
|---|---|
| **圧縮ファイル全体のハッシュ** | 堅牢・リネーム耐性あり・content-addressed。大容量 zip だと計算コスト |
| **先頭 N バイト + サイズ** の部分ハッシュ | 大容量で高速、衝突リスク微小 |
| **パス + mtime + サイズ** | 最速だが、コピー間で dedup 不可・mtime 変化で誤判定 |
| **解凍後コンテンツのハッシュ** | 一度解凍が必要でキャッシュキーには不向き |

## 他エミュの先例

- **MAME**: ROM は zip から read-only 展開。書込可能な HDD（CHD）は `diff` ディレクトリに
  **差分ファイル**を作る → 方式 D。元イメージは絶対に書き換えない。
- **RetroArch/libretro**: 「キャッシュディレクトリ」へ展開して再利用 → 方式 B。
- **DOSBox 等**: zip は read-only マウント → 方式 A。

## Bubilator の採用方式

- **方式 B（解凍コピーを正本化）**: 解凍物を一時ファイルにせず永続化。
- **キー = 圧縮ファイルのハッシュ**。ハッシュ値でフォルダを作りそこに解凍。以後ハッシュが同一なら
  展開済みファイルを再利用。
- RetroArch 系の実績ある選択。

### 方式 B を採る場合に詰めるべき点

1. **キャッシュ退避（eviction）**: 展開物が無限に溜まる。LRU / 総容量上限 /
   「元 zip が消えたらキャッシュも消す」等のポリシーが要る。
2. **書き戻し方針の明文化**: 「セーブは展開コピーに残り zip には戻さない」が暗黙仕様。
   ユーザが zip を作り直す / 別マシンに zip を持っていくとセーブが付いてこない。
3. **大容量 HDD**: FDD（1.2/1.44MB）は軽いが、HDI が数十〜数百 MB だと丸ごと複製がディスクを圧迫。

## UsaProject 向けの方針案

- **FDD（小容量）**: 方式 B、またはメモリ展開 + 差分サイドカーで十分軽い。
- **HDD（大容量）**: 元 zip を不変のまま **方式 D（差分オーバーレイ）** が最も無駄がなく安全。
  np2kai には既に **差分 VHD（`fdd/hdd_vhd.h`）** の素地があり、「圧縮元 = 親、書き込み = 子 VHD」
  に見立てると D が自然に実装できる。
- **キーはハッシュ**。大容量 zip 対策として「サイズ + 先頭/末尾チャンクのハッシュ」への妥協も可。
- 解凍・キャッシュ・差分の制御は**コアに手を入れず Zig アプリ層**に置くのが `AGENTS.md` の方針に合致。
